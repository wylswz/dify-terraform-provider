# Contributing to terraform-provider-dify

Thanks for your interest in contributing! This document covers how to build,
test, lint, and document the provider.

## Development Setup

Requirements:

- [Go](https://go.dev/dl/) (see `go.mod` for the required version)
- [Terraform](https://developer.hashicorp.com/terraform/install) >= 1.0
- [golangci-lint](https://golangci-lint.run/welcome/install/) for `make lint`
- A Dify instance for manual/acceptance testing (a local [self-hosted
  deployment](https://github.com/langgenius/dify) works fine)

```bash
git clone https://github.com/wylswz/dify-terraform-provider.git
cd dify-terraform-provider
go build ./...
```

## Building and Installing Locally

```bash
# Build the provider binary
make build          # go build -v ./...

# Install into $GOBIN (e.g. ~/go/bin) for `terraform init` dev overrides
make install

# Install into the local plugin mirror
# (~/.terraform.d/plugins/registry.terraform.io/dify/dify/<version>/<os>_<arch>)
make install-local
```

To point Terraform at your local build, either use `make install-local` or add
a [CLI dev override](https://developer.hashicorp.com/terraform/cli/config/config-file#development-overrides-for-provider-developers)
to `~/.terraformrc`:

```hcl
provider_installation {
  dev_overrides {
    "registry.terraform.io/dify/dify" = "/path/to/go/bin"
  }
  direct {}
}
```

## Testing

```bash
# Unit tests (no Dify instance needed — they run against httptest servers)
make test

# Acceptance tests against a live Dify instance
export DIFY_HOST="http://localhost"
export DIFY_TOKEN="<personal-access-token>"
export DIFY_WORKSPACE_ID="<workspace-id>"   # optional
make testacc
```

Unit tests must pass in CI. Please add or update tests for any client or
resource behavior you change — see `internal/provider/*_test.go` for the
httptest-based patterns.

## Linting

```bash
make lint       # golangci-lint run ./...
make fmt        # gofmt -s -w + terraform fmt -recursive ./examples/
```

CI fails if `golangci-lint` reports issues or if the tree is not
`gofmt -s`-clean.

## Documentation

Documentation under `docs/` is generated by
[tfplugindocs](https://github.com/hashicorp/terraform-plugin-docs) from schema
descriptions (`MarkdownDescription`), the `templates/` directory, and runnable
examples under `examples/`.

```bash
make generate   # terraform fmt examples + regenerate docs/
```

When you change a schema description or an example, run `make generate` and
commit the updated `docs/` — CI verifies they are in sync.

- Resource docs: `templates/resources/<name>.md.tmpl` (optional override;
  the default template is used when absent)
- Examples: `examples/resources/<type>/resource.tf`,
  `examples/data-sources/<type>/data-source.tf`,
  `examples/resources/<type>/import.sh` for importable resources

## Commit Style

Use concise commit messages that explain *why* a change is needed, e.g.
`fix(tools): match provider name exactly in node_data filter`. For a specific
scope, follow the existing convention (`feat(area):`, `fix(area):`,
`docs:`, `chore:`).

## Releasing

Releases are cut from version tags (`v*`). The `release` GitHub Actions
workflow runs GoReleaser to build cross-platform archives, generate the
checksum manifest, sign it with the maintainer GPG key, and attach everything
to a GitHub release — the format the Terraform Registry consumes.

Before tagging, update `CHANGELOG.md` with the release notes.
